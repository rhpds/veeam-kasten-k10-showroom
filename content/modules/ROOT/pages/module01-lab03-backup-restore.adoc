= Protecting VMs

== 1. Introduction

In this exercise you will create and run a Kasten *_Virtual Machine policy_* for protecting Virtual Machines running on OpenShift and test restoring from both local and remote backup sources.

== 3. Enabling Block Mode Exports

====
[NOTE]

As some storage provisioners may not fully support Block volume mode, StorageClasses should first be evaluated for compatibility https://docs.kasten.io/latest/operating/k10tools.html#k10-primer-block-mount-check[using the primer script].
This is skipped in the lab exercise as the `openshift-storage.rbd.csi.ceph.com` provisioner is known to be compatible.
====

. Your `StorageClass` has already been set up to allow the Kasten datamover to export raw Block volumes using the `{kasten_storageclass}` StorageClass:
+
In the *_Web Terminal_*, run the following command to validate that the annotation is present (you should see an annotation starting with `k10.kasten.io`):
+
[source,bash,role=execute,subs="attributes"]
----
oc get sc {kasten_storageclass} -ojsonpath='{.metadata.annotations}';echo
----
+
====
[TIP]

The command to annotate the storage class would be (you don't need to execute this):

[source,bash]
----
oc annotate storageclass {kasten_storageclass} \
  k10.kasten.io/sc-supports-block-mode-exports=true
----
====
+
By default, Kasten provides an out-of-the-box, direct API integration with ODF's Ceph Volume Manager for block data movement - including support for incremental backups to lower storage consumption requirements for protecting Virtual Machines.
+
====
[IMPORTANT]

While many Kubernetes backup solutions can orchestrate local CSI snapshots of a `volumeMode: Block` PVC, it is important to remember that _snapshots do not equal backup_ - and that having a backup solution that can provide off-cluster data movement for `volumeMode: Block` PVCs is critical.
Support for this capability does *NOT* exist in Velero or OADP today.
====

== 4. Creating a Kasten Virtual Machine Policy

Traditionally, Kasten policies select *_applications_* by namespace (or by labels), capturing every resource in the namespace as a single RestorePoint.
While this works well for containerized applications, it can be limiting for Virtual Machines - restoring a single VM from a namespace containing many VMs becomes more complex, and a failure protecting one VM can affect the others.

Kasten *_Virtual Machine policies_* treat each `VirtualMachine` as a first-class object:

* VMs are selected by namespace and VM name (including wildcards), or by labels on the `VirtualMachine` resource
* Each VM gets its own RestorePoint, along with its automatically discovered dependencies (DataVolumes, PVCs, InstanceTypes, Preferences, Secrets, ConfigMaps, etc.)
* Multiple VMs can live in the same namespace while still being protected, monitored, and restored individually

. In the *_Kasten Dashboard_*, select *_Applications_* to view all discovered namespaces.
+
image::module01-lab03-backup_restore/07.png[]
+
Your `kasten-lab-{user}` application should appear as *_Unmanaged_*, indicating it is not being protected by any policy.
+
====
[TIP]

Namespaces, including the `+openshift-...+` system namespaces can be excluded from the *_Applications_* list (and compliance reporting) by adding a list of `excludedApps` to the K10 Operand `spec`, as shown:

image::module01-lab03-backup_restore/08.png[]

The following command can be used to produce a properly formatted list of namespaces beginning with `openshift` that can be copy/paste into the K10 Operand YAML tab:

[source,bash,role=execute,subs="attributes"]
----
oc get ns --no-headers=true | \
  awk 'BEGIN { print "  excludedApps:" } /^openshift/{print "  -",$1}'
----
====

The *_Virtual Machines_* dashboard provides a cluster-wide view of every VM Kasten has discovered, including its namespace, status, whether guest filesystem freeze is enabled, and when it was last backed up.

image::module01-lab03-backup_restore/10a.png[]

[NOTE]

Toggling *_Advanced Frequency Options_* allows users to specify what time hourly snapshots occur, how many snapshots to take per hour, and which snapshots should be used for daily, weekly, monthly, and yearly promotion.

Toggling *_Backup Window_* allows users to specify during what times is Kasten allowed to run the policy.

However, there are circumstances where you may only want to export references to the snapshot, such as migrating a workload in AWS from one availability zone to another.

image::module01-lab03-backup_restore/14b.png[]

====
[NOTE]

Alternatively, selecting *_By Labels_* allows you to protect current and *_future_* VMs with a specific label on the `VirtualMachine` resource, such as `backup: gold` or `vm: prod`, across all namespaces or only within namespaces matching a pattern (ex. `prod-*`).
The label selector is re-evaluated each time the policy runs.
====

. Under *_Select VM Resources_*, leave *_All VM Dependencies_* selected.
+
image::module01-lab03-backup_restore/14c.png[]
+
====
[NOTE]

Kasten automatically discovers the resources each VM depends on by following references in the `VirtualMachine` spec, such as DataVolumes, PVCs, InstanceTypes, Preferences, ConfigMaps, Secrets, and NetworkAttachmentDefinitions.

*_Filter VM Dependencies_* allows you to include or exclude specific discovered dependencies, while *_Select Additional Resources_* allows you to include other namespaced resources not referenced by the VM, such as a `Service` or a detached PVC.
====

. Click the *_</> YAML_* button at the bottom of the form to view the native Kubernetes YAML that defines the policy.
+
image::module01-lab03-backup_restore/14d.png[]
+
Note the `selector` uses the `k10.kasten.io/virtualMachineRef` key with a value of `<namespace>/<vm-name>`.
Wildcards are supported for the VM name (ex. `kasten-lab-{user}/*`).
A label-based VM policy would instead look like:
+
[source,yaml]
----
  selector:
    matchExpressions:
      - key: k10.kasten.io/virtualMachineNamespace
        operator: In
        values:
          - "*"
    matchLabels:
      backup: gold
----
+
====
[TIP]

When performing many tasks within the Kasten UI, you can press the *_</> YAML_* button to expose the native Kubernetes YAML that defines the resource created through the UI.
This can be useful for familiarizing yourself with the Kubernetes-native APIs defined by Kasten and for extracting snippets for use in GitOps or Infrastructure-as-Code tools.
====

. Close the YAML window and click *_Submit_*.

== 5. Freezing the Guest Filesystem

Kasten freezes the guest filesystem before taking a snapshot of a *_Running_* VM and unfreezes it after the snapshot completes, using the QEMU guest agent (`fsfreeze` on Linux, VSS on Windows) to produce a consistent backup.
Guest filesystem freeze is *_enabled by default_*, as shown in the *_Freeze Guest_* column of the *_Virtual Machines_* dashboard.

. In the *_Kasten Dashboard_*, select *_Virtual Machines_* from the sidebar and click the *_..._* menu for `{user}-fedora`.
+
image::module01-lab03-backup_restore/14a.png[]
+
Selecting *_Disable guest OS Freeze_* would disable filesystem freezing for the VM.
Freeze can also be enabled or disabled for multiple VMs at once by selecting their checkboxes and using the *_Actions_* menu.
*_Leave guest filesystem freeze enabled for this lab._*
+
====
[NOTE]

The UI manages the `k10.kasten.io/freezeVM` annotation on the `VirtualMachine` resource.
The same result can be achieved from the command line (you don't need to execute this):

[source,bash,subs="attributes"]
----
oc annotate virtualmachine {user}-fedora \
  -n kasten-lab-{user} \
  k10.kasten.io/freezeVM=false
----

The annotation can also be applied to a namespace, in which case all VMs in the namespace inherit the setting unless individually annotated.
If the freeze operation fails, Kasten falls back to a crash-consistent snapshot and records the event as an exception.
====
+
====
[WARNING]

Kasten defines a 5 minute default timeout for the snapshot operation to complete before aborting the snapshot operation and unfreezing the VM.
This can be overridden using the `kubeVirtVMs.snapshot.unfreezeTimeout` Helm/Operand parameter.
====

== 7. Performing a Local Restore

When performing an in-place restore on the application's original cluster, choosing the local RestorePoint provides the most rapid recovery as it uses the snapshot data already present on primary storage, rather than having to depend on data which must be transferred from the remote repository.

. In the *_Kasten Dashboard_*, select *_Virtual Machines_* from the sidebar.
+
You should observe that the *_Last Backup_* column for `{user}-fedora` now displays the time of your policy run.

. Click the *_..._* menu for `{user}-fedora` and select *_Restore_*.
+
image::module01-lab03-backup_restore/19.png[]
+
You will be taken to the *_Restore Points_* page, filtered to the *_Virtual Machine_* application type and your `{user}-fedora` VM.
Each policy run produces a local *_Snapshot_* RestorePoint and an *_Exported_* RestorePoint in the `kastenbackups-{user}` Location Profile.

. Click the *_..._* menu for the most recent RestorePoint of type *_Snapshot_* and select *_Restore_*.
+
image::module01-lab03-backup_restore/20.png[]
+
You should observe by default the selected RestorePoint will be restored to its original namespace - with options to restore to a new namespace, perform a data-only restore, or preserve the VM's original MAC addresses.

. Keep the default settings and click *_Restore_* to begin a full, in-place restore.
+
image::module01-lab03-backup_restore/21.png[]
+
====
[WARNING]

Kasten will terminate the running VM and overwrite the existing resources.
However, any resources in the namespace that do not exist in the RestorePoint will not be altered (protecting against unintentional data loss).
====

. Confirm the restore action by clicking *_Restore_*.
+
image::module01-lab03-backup_restore/21a.png[]

. Return to the *_Dashboard_* to monitor the status of the *_Restore_* under *_Actions_*.
+
You should expect this operation to complete rapidly (less than 2 minutes), as the VM volume is being restored from a local CSI VolumeSnapshot.

. Once the *_Restore_* has completed, return to *_OpenShift Console → Virtualization → VirtualMachines_*, select the `kasten-lab-{user}` project in the tree, and click the *_Virtual machines_* tab.
+
You will notice the `{user}-fedora` VM has been restored in a *_Stopped_* state.
+
====
[NOTE]

The power state of a restored VM depends on its `spec.runStrategy`.
During an in-place restore, Kasten shuts down the running VM before overwriting its resources.
VMs created through the OpenShift Console default to `runStrategy: RerunOnFailure`, which only restarts a VM after a failure - not after a clean shutdown - so the VM remains *_Stopped_* once the restore completes.
VMs using `runStrategy: Always` are started automatically, while `Halted` and `Manual` VMs are always left stopped.

You can check the run strategy of your VM by running:

[source,bash,role=execute,subs="attributes"]
----
oc get vm {user}-fedora -n kasten-lab-{user} -o jsonpath='{.spec.runStrategy}';echo
----
====

. Click the *_..._* menu for `{user}-fedora` and select *_Control → Start_*.
+
image::module01-lab03-backup_restore/21b.png[]

. Validate the `{user}-fedora` VM is *_Running_*.
+
image::module01-lab03-backup_restore/22.png[]
+
====
[NOTE]

You can also validate the source of the restored volume by running:

[source,bash,role=execute,subs="attributes"]
----
oc describe pvc {user}-fedora-volume -n kasten-lab-{user}
----

You should observe the volume's *_DataSource_* is a `+k10-csi-snap-...+` VolumeSnapshot, confirming the volume was restored from a local snapshot.
====

== 8. Performing a Remote Restore

Often, local snapshot data may not be available, requiring that data be restored from the remote Kasten repository.

. In the *_Web Terminal_*, run the following to delete the `kasten-lab-{user}` namespace:
+
[source,bash,role=execute,subs="attributes"]
----
oc delete virtualmachine {user}-fedora -n kasten-lab-{user}

oc delete project kasten-lab-{user}
----
+
====
[IMPORTANT]

_"Snapshots are not backup."_              ~ Mark Twain

Local snapshots live on the same primary storage as the workload they protect.
If the cluster, the storage system, or the snapshots themselves are lost or compromised, only a copy exported to a separate Location Profile can be used for recovery.
In this exercise you will simulate that scenario by deleting the VM and its namespace and restoring exclusively from the *_Exported_* RestorePoint.
====

. In the *_Kasten Dashboard_*, select *_Virtual Machines_* from the sidebar.
+
You should observe that `{user}-fedora` no longer appears in the list as the VM no longer exists on the cluster.

. Select *_Restore Points_* from the sidebar and select *_Virtual Machine_* as the *_Application type_*.
+
image::module01-lab03-backup_restore/23.png[]
+
RestorePoints for the deleted `{user}-fedora` VM are still available even though the VM and its namespace no longer exist on the cluster.
You may also see an additional pair of RestorePoints if the hourly policy schedule has run since your manual backup.

. Click the *_..._* menu for the most recent *_Exported_* RestorePoint and select *_Restore_*.
+
image::module01-lab03-backup_restore/24.png[]

. Under *_Namespace_*, click *_Create A New Namespace_*.
. Specify `kasten-lab-clone-{user}` as the *_New Namespace_* and click *_Create_*.
+
image::module01-lab03-backup_restore/25.png[]
+
====
[WARNING]

Make sure to click the *_Create_* button to create the new namespace!
====

. Click *_Restore_*, then in the confirmation dialog click *_Restore_* again.
+
image::module01-lab03-backup_restore/25a.png[]

. Return to the *_Dashboard_* to monitor progress under *_Actions_*.
+
image::module01-lab03-backup_restore/26.png[]

. Once the *_Restore_* has completed, return to *_OpenShift Console → Virtualization → VirtualMachines_* and select the `kasten-lab-clone-{user}` project.
Observe the `{user}-fedora` VirtualMachine now running in the `kasten-lab-clone-{user}` namespace.
+
image::module01-lab03-backup_restore/27.png[]
+
====
[NOTE]

Unlike the in-place restore, restoring to a new namespace creates a brand new `VirtualMachine` resource, so a `RerunOnFailure` VM is started automatically.
If your VM shows as *_Stopped_*, click the *_..._* menu and select *_Control → Start_*.
====
+
====
[NOTE]

Unlike the local restore, the PVC populated by the Kasten datamover will not contain a *_DataSource_* snapshot reference:

[source,bash,role=execute,subs="attributes"]
----
oc describe pvc {user}-fedora-volume -n kasten-lab-clone-{user}
----
====

== 9. Takeaways

_Congratulations on having protected and restored your first workload using Veeam Kasten!_ Below are some of the key takeaways of what has been covered in the lab so far:

* Kasten runs on the cluster and can be deployed via OperatorHub or Helm chart
* Kasten supports multiple authentication options (Tokens, OIDC, LDAP, OpenShift OAuth) and Kubernetes-native RBAC for controlling access and providing per-namespace self-service
* Kasten can backup data to S3, Azure Blob, Google Cloud Storage, NFS/SMB, Veeam Data Cloud Vault, and Veeam Backup & Replication
* Immutable backup support prevents unintended or malicious attempts to delete backup data, providing critical protection against ransomware
* Kasten *_Virtual Machine policies_* protect each VM - and its automatically discovered dependencies - as a first-class object with its own RestorePoints, selected by name, wildcard, or label
* Guest filesystem freeze is enabled by default to provide consistent VM backups
* `Block` mode volumes can provide `ReadWriteMany` access using Ceph RBD, the most performant option for enabling Live Migration of OpenShift Virtual Machines
* Kasten performs always incremental backups with support for both `Filesystem` and `Block` mode volumes
